# 🚀 이미지 업로드 파이프라인 개선 회고 ✨

## 📌 개요

본 문서는 지난 분기에 진행하였던 이미지 업로드 파이프라인 개선 작업에 있어서의 경과와 결과를 정리하고 있으며, 향후 유사한 작업을 수행하는 데 있어 참고가 될 수 있는 시사점을 도출하고자 작성되었습니다. 기존 파이프라인의 경우 업로드된 원본 이미지를 동기적으로 리사이즈하는 방식을 채택하고 있었는데, 이는 대용량 파일이 유입될 때마다 요청 스레드가 장시간 점유되는 결과를 초래하였으며, 결과적으로 전체 응답 지연이 증가할 수 있는 여지가 있다고 볼 수 있습니다.

**따라서 비동기 처리 방식으로의 전환을 진행하였습니다.**

## 작업 내역

- 업로드 엔드포인트에서 원본만 저장하도록 변경합니다
- 리사이즈 작업을 큐로 분리
- 워커 프로세스를 신규로 추가함
- 실패한 작업은 3회까지 재시도하도록 한다
- 처리 완료 시 웹훅으로 통지합니다

작업 순서는 먼저, 스토리지 스키마를 변경하였고, 다음으로, 큐 인프라를 구축하였으며, 마지막으로, 기존 동기 코드를 제거하는 순으로 진행하였습니다.

## 측정 결과

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| p95 응답시간 | 2,400ms | 180ms |
| 워커 처리량 | — | 초당 40건 |
| 실패율 | 0.8% | 0.3% |

수치를 확인해 보면 응답시간의 개선이 극대화되었음을 확인할 수 있으며, 이는 본 전환이 서비스 품질 측면에 있어 중요한 역할을 하였음을 시사한다고 볼 수 있습니다.

## 회고

큐를 도입하는 것은 단순히 성능을 개선하는 것이 아니라 장애 격리 지점을 하나 더 확보하는 것이며, 운영 편의성 측면에 있어서도 상이한 접근을 가능하게 하였습니다. 다만 초기 설계 시에 재시도 정책을 명확히 기입하지 않았던 관계로, 워커 배포 중에 중복 처리가 발생하는 이슈가 있었고 이를 멱등키 도입을 통해 해결하였는데 이 과정에서 약 이틀 정도가 소요되었습니다.

> 인프라 팀 회신 원문: "큐 사용량이 예상보다 높습니다. 다음 분기 용량 산정에 반영하겠습니다."

재시도 로직의 핵심은 아래와 같습니다.

def process(job):
    if seen(job.idempotency_key):
        return
    resize(job.src, job.sizes)
    mark(job.idempotency_key)
