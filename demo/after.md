# 이미지 업로드 파이프라인 개선 회고

## 개요

지난 분기에 이미지 업로드 파이프라인을 비동기 방식으로 바꿨습니다.
무엇을 했고 무엇이 달라졌는지, 다음에 비슷한 작업을 할 때 참고할 것을 적었습니다.

전에는 업로드된 원본을 그 자리에서 리사이즈했습니다.
큰 파일이 들어올 때마다 요청 스레드가 오래 잡혀 있었고, 그만큼 응답이 느려졌습니다.

## 작업 내역

- 업로드 엔드포인트에서 원본만 저장
- 리사이즈 작업을 큐로 분리
- 워커 프로세스 추가
- 실패한 작업 3회까지 재시도
- 처리 완료 시 웹훅으로 통지

순서는 셋으로 나눴습니다.

- 스토리지 스키마 변경
- 큐 인프라 구축
- 기존 동기 코드 제거

## 측정 결과

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| p95 응답시간 | 2,400ms | 180ms |
| 워커 처리량 | — | 초당 40건 |
| 실패율 | 0.8% | 0.3% |

p95 응답시간이 2,400ms 에서 180ms 로 내려갔습니다.

## 회고

큐를 넣어서 얻은 것은 속도만이 아닙니다.
장애가 번지는 것을 끊는 지점이 하나 늘었고, 운영할 때 손 댈 수 있는 폭도 넓어졌습니다.

처음 설계할 때 재시도 정책을 적어 두지 않은 것이 문제였습니다.
워커를 배포하는 중에 같은 작업이 두 번 처리됐고, 멱등키를 넣어 막았습니다.
여기에 이틀이 걸렸습니다.

> 인프라 팀 회신 원문: "큐 사용량이 예상보다 높습니다. 다음 분기 용량 산정에 반영하겠습니다."

재시도 로직의 핵심은 아래와 같습니다.

```python
def process(job):
    if seen(job.idempotency_key):
        return
    resize(job.src, job.sizes)
    mark(job.idempotency_key)
```
